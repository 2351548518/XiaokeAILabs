# 03：沿 train.py 理解训练、选优、校准和测试

本文按当前 [train.py](../scripts/train.py) 的执行顺序讲解。
数值实例引用已完成的 `runs/agentjev_v1/`，没有在写文档时启动训练。
指标衡量的是与公开教师标签的关系，不代表真实 Agent 执行成功率。

## 1. main() 之前：路径和 GPU 设置

对应代码：[模块级设置](../scripts/train.py#L11)、[train.main](../scripts/train.py#L209)。

`ROOT` 取脚本上两级的 `text_jev_train/`，并加入 `sys.path`，
这样脚本可以导入同目录的 agentjev 和 jev_service 包。

当前源码在导入 torch 之前直接设置：

```python
os.environ["CUDA_VISIBLE_DEVICES"] = "3"
```

因此它只暴露物理 GPU 3，后续的 `cuda:0` 是该进程的逻辑设备 0。
当前这行会覆盖 shell 传入的同名环境变量；不能仅在命令前设置另一个编号，
就假定本训练脚本会使用那张卡。训练代码也没有 DDP 或多卡梯度同步。
这一行为属于当前源码状态，不能用来反推旧运行究竟使用了哪张物理卡。

main 接收的主要参数：

| 参数 | 含义 |
|---|---|
| --backbone | 必填，本地 Qwen3 权重和 tokenizer 目录 |
| --protocol | 超参数 JSON，默认 scripts/protocol.json |
| --prepared | 切分后的数据目录，默认 prepared/ |
| --run-dir | 本次运行的产物目录，建议始终显式指定新目录 |

若运行目录已有 `selection.json`，程序拒绝继续，以免覆盖已完成选优的运行。
没有 selection.json 的失败目录不受这个保护，不应把它理解成完整断点续训功能。

## 2. 初始化与第 0 步评估

对应代码：[随机种子与 tokenizer](../scripts/train.py#L228)、
[加载 train/dev 和输入审计](../scripts/train.py#L239)、
[初始化评估与保存](../scripts/train.py#L257)。

按顺序执行：

1. 读取 protocol，设置 PyTorch 种子、本地 Python 随机数生成器和 CPU 线程数。
2. 从本地加载 tokenizer；`pad = tok.pad_token_id or tok.eos_token_id`。
   当前 pad 为 151643，所以选中 pad。一般化时要注意 ID 为 0 会被这个 or 当成假值。
3. 读取 train 和 dev 的 questions，调用 tokenize，构造候选路径。
4. 保存 `input_audit.json`：题数、路径长度和输入字段声明。
5. 加载 Qwen3，随机初始化候选头，整体放到逻辑 `cuda:0`。
6. 在 dev 上评估，保存 `initial_dev.json`，并把第 0 步权重保存为 `best.pt`。

这里的“初始化”表示尚未做本次决策训练，骨干仍有下载来的 Qwen 权重。
保存第 0 步的原因是它也参与选优：如果训练后的 dev 指标始终更差，
最终仍有一个可用的最佳 checkpoint 来校准和测试。

此时尚未读取 calibration 和 test。

主干代码摘录如下；这几行读取的只有 train 和 dev：

```python
train_rows = tokenize(load("train", prepared_dir), tok)
dev_rows = tokenize(load("dev", prepared_dir), tok)
```

完成输入审计和模型构建之后：

```python
base = evaluate(model, dev_rows, pad)
best_ce = metrics(base)["soft_cross_entropy"]
if not math.isfinite(best_ce):
    raise RuntimeError("nonfinite initial development loss")
best_step = 0
```

随后调用 `save_checkpoint(model, run_dir, best_step, protocol)`。
这里把 best_step 设成 0，解释了为什么尚未更新参数也会有 best.pt。

## 3. 优化器、学习率和有效批次

对应代码：[AdamW 参数分组](../scripts/train.py#L269)、
[LambdaLR 调度](../scripts/train.py#L282)、[protocol.json](../scripts/protocol.json)。

当前 protocol 设置：

| 配置 | 值 | 解释 |
|---|---:|---|
| microbatch_questions | 1 | 每次前向/反向处理 1 道题 |
| gradient_accumulation | 16 | 累积 16 次之后更新一次参数 |
| max_steps | 600 | 600 次优化器更新 |
| backbone_lr | 1e-5 | 骨干的基准学习率 |
| head_lr | 1e-4 | 新候选头的基准学习率 |
| warmup_steps | 20 | 学习率预热长度 |
| weight_decay | 0.01 | AdamW 权重衰减 |
| grad_clip | 1.0 | 整体梯度范数裁剪阈值 |

凡参数名称包含 `.backbone.` 的分入骨干组，其余进入候选头组。
两组都更新，没有冻结骨干，也没有使用 LoRA。AdamW 会为可训练参数维护优化状态。
代码没有单独为 bias 或归一化参数配置免衰减分组。

单卡有效批量是 `1 × 16 = 16` 道题，而不是 16 个案例或 16 条路径。
题目根据候选数展开，单次 1 题也可能包含 2、4、5 条实际 token 序列。
600 次更新累计抽取 9600 道题，相对于 4800 道训练题恰为两轮。
采样是先打乱题目索引，读完后再打乱继续，并不是每一步独立有放回随机抽样。

LambdaLR 对两组基准学习率乘相同系数：先线性预热，再按余弦衰减。
源码使用 `(s+1)/warmup`，因此初始系数是 `1/20`，首次优化器更新的学习率非零。
`opt.step()` 在前、`schedule.step()` 在后，后者设置下一次更新使用的学习率。

FP32 权重不等于所有算子都用 FP32；前向放在 BF16 autocast 中。
当前没有启用梯度检查点。减小 microbatch 可减少部分激活显存，但不会消除权重、
梯度、AdamW 状态的开销，显存也不能简单按 microbatch 的比例缩放。

## 4. 一次优化器更新发生什么

对应代码：[训练外循环与梯度累积](../scripts/train.py#L294)、
[反向传播和优化器更新](../scripts/train.py#L316)。

外层的一个 step 对应一次参数更新，内部重复 16 次：

```text
model.train()
清空上一步梯度
    取1题 → batch → BF16前向 → 屏蔽补齐候选
    → 计算损失 → loss/16 反向传播
    ……重复16次，梯度累加到同一批参数上……
裁剪累计梯度
AdamW更新一次
学习率调度一次
记录step、平均loss和耗时
```

`model.train()` 每步都会调用，所以前一次 dev 评估设置的 eval 模式会被恢复。
循环内部不调用 zero_grad，才能累积梯度；除以 16 是使累计梯度对应 16 题的平均损失。
梯度裁剪和 optimizer.step 也都在累积完成后进行。

与上面流程对应的源码摘录，分成两个连续阶段。第一段位于梯度累积循环内部：

```python
(loss / protocol["gradient_accumulation"]).backward()
total_loss += float(loss.detach()) / protocol["gradient_accumulation"]
```

第二段在整个累积循环结束后执行：

```python
norm = torch.nn.utils.clip_grad_norm_(
    model.parameters(), protocol.get("grad_clip", 1.0)
)
if not torch.isfinite(norm):
    raise RuntimeError("nonfinite gradient")
opt.step()
schedule.step()
```

因此不是每做一道题就 AdamW 更新一次。以累积 16 次为例，第一段执行 16 次，
第二段执行 1 次，随后才进入下一个外层 step。

## 5. 损失怎样算：以真实 action 题为例

对应代码：[训练循环中的屏蔽与损失计算](../scripts/train.py#L309)。

先看实际实现，再与下面的公式和真实概率对照：

```python
logits = logits.float().masked_fill(~b["cand_mask"], float("-inf"))
logp = torch.log_softmax(logits, -1).masked_fill(~b["cand_mask"], 0)
p = logp.exp() * b["cand_mask"]
ce = -(b["target"] * logp).sum(-1).mean()
loss = ce + 0.1 * ((p - b["target"]) ** 2).sum(-1).mean()
```

这里张量形状都是 `[Bq,Cmax]`：`sum(-1)` 对候选求和，`mean()` 再对题目取平均。
两题示例中的第二题有两个补齐候选，正是这些 masked_fill 和 mask 乘法将它们排除。

模型输出 z，首先用 cand_mask 将补齐项设为 `-inf`，再计算 log_softmax。
随后把无效位置的 logp 设为 0，避免后面出现 `0 × -inf`；
`p = exp(logp) * cand_mask` 又把无效位置概率恢复为 0。

逐题计算两项，最后在题目维度取平均：

```text
soft CE = -sum(target[c] * log(probability[c]))
Brier   =  sum((probability[c] - target[c])²)
loss    = soft CE + 0.1 * Brier
```

候选维度是求和，不是按候选数平均；每道题在 microbatch 中的权重相同。
这里并没有把 target.argmax 当作交叉熵的整数标签。
三种题型都使用同一套 softmax 和分布损失：boolean 没有单独的 sigmoid/BCE 分支，
score 也没有单独的数值回归损失；其等级次序主要体现在描述、输出期望和测评中。

上一篇 CPU 前向得到的 action 概率为：

```text
target: [0.073333, 0.570000, 0.296667, 0.060000]
pred:   [0.089912, 0.564414, 0.280673, 0.065001]

soft CE ≈ 1.043611
Brier   ≈ 0.000586856
loss    ≈ 1.043669
```

needs_review 的 loss 约为 0.636559。
如果把两题作为一个 microbatch，其平均 loss 约为 0.840114；
这只是本次 CPU 解释用的两题批次，原运行的训练 microbatch 实际为 1。

预测分布已经很接近 target，CE 仍约为 1，是因为标签自身并非独热分布。
当预测等于 target 时，软 CE 等于该题 target 的熵，不要求趋近 0。
因此不能拿普通单标签分类“loss 越接近零越好”的直觉判断这里是否训练成功。

记录到 events 的 loss 是当前一次更新内的平均混合损失，不是整个训练集的平均值。
不同步骤取到不同题目，出现上下波动正常。

## 6. evaluate() 与 metrics() 的分工

对应代码：[evaluate](../scripts/train.py#L162)、[metrics](../scripts/train.py#L113)、
[report](../scripts/train.py#L148)、[probabilities](../scripts/train.py#L106)。

`evaluate()` 执行以下过程：

1. model.eval，关闭训练模式相关行为。
2. 每次取 8 道题，调用同一个 batch。
3. 使用 inference_mode 关闭梯度记录，并启用 CUDA BF16 autocast。
4. 获取 logits，转 FP32、CPU 和 Python 列表。
5. 按 target 长度剔除补齐候选，调用 probabilities 得到未校准分布。
6. 返回 id、case_id、workflow、target、type、logits、probs。

固定的评估题数 8 与训练 microbatch=1 无关。评估没有反向传播，
所以训练放不下 8 题，并不意味着评估一定也放不下；但它仍会消耗显存。
evaluate 本身不计算准确率，也不把 target 输入给骨干。

评估中的核心代码摘录：

```python
for start in range(0, len(rows), 8):
    chunk = rows[start : start + 8]
    b = batch(chunk, pad)
    with torch.inference_mode(), torch.autocast("cuda", dtype=torch.bfloat16):
        logits = model(b)["logits"].float().cpu().tolist()
    for r, z in zip(chunk, logits):
        z = z[: len(r["target"])]
        predictions.append(
            {k: r[k] for k in ("id", "case_id", "workflow", "target")}
            | {"type": r["question"]["type"], "logits": z, "probs": probabilities(z)}
        )
```

`z[:len(target)]` 先去掉补齐候选，再计算概率；字典合并保留标签供后续指标比较。

`metrics()` 再比较 probs 与 target；`report()` 把同一套指标分别按
overall、by_type、by_workflow 汇总：

| 指标 | 当前代码含义 | 方向 |
|---|---|---|
| n | 决策题数，不是案例数 | — |
| accuracy | 预测 argmax 是否等于教师 target 的 argmax | 高 |
| soft_cross_entropy | 与教师完整分布的交叉熵 | 低 |
| brier_sum | 各候选概率平方误差求和，再跨题平均 | 低 |
| gold_mass_at_selected_option | 预测选中项在教师分布中的概率，再跨题平均 | 高 |
| ece_10_bins_vs_gold_argmax | 按最高预测概率分10箱，比较箱内准确率与置信度 | 低 |
| score_expectation_mae | 仅 score：预测期望等级与教师期望等级的绝对误差 | 低 |

score 等级索引从 0 开始。例如真实 risk 题的教师分布
`[0.08,0.286667,0.513333,0.12]` 对应期望为 `1.673333`，
不是 0 到 1 归一化后的风险，也不一定等于最大概率等级 2。

## 7. dev 如何选择 best.pt

对应代码：[dev 验证与 best.pt 替换](../scripts/train.py#L326)。

```python
if step % 100 == 0 or step == steps:
    pred = evaluate(model, dev_rows, pad)
    m = metrics(pred)
    rec["dev"] = m
    if m["soft_cross_entropy"] < best_ce:
        best_ce = m["soft_cross_entropy"]
        best_step = step
        save_checkpoint(model, run_dir, step, protocol)
    save(run_dir / f"dev_step_{step}.json", report(pred))
```

对照最后两行：每次验证都保存自己的 dev 报告，但只有改进时才替换模型权重。

初始化、每 100 次更新及最后一步执行 dev 评估。
仅当新的未校准 `soft_cross_entropy` 严格小于当前最佳值，才替换 best.pt。
不会依据训练 loss、test accuracy 或校准后的结果选模型。

本地已完成运行的实际记录：

| 检查点 | dev accuracy | dev soft CE |
|---|---:|---:|
| 初始化 | 0.273333 | 1.213610 |
| step 100 | 0.683333 | 0.960968 |
| step 200 | 0.711667 | 0.954185 |
| step 300 | 0.756667 | 0.859358 |
| step 400 | 0.780000 | 0.829902 |
| step 500 | 0.790000 | 0.823815 |
| step 600 | 0.798333 | 0.820790 |

因此本次选择 step 600。当前训练按 max_steps 完成，没有因指标不再改善而提前停止。

## 8. 校准只调整温度，不重新训练权重

对应代码：[calibrate](../scripts/train.py#L179)、
[apply_calibration](../scripts/train.py#L202)、[加载最佳权重和校准集](../scripts/train.py#L350)。

选优结束后先保存 selection.json，然后重新加载 best.pt。
此时才读取 calibration，评估出原始 logits。
每种题型单独尝试 81 个按对数均匀排列的正温度，范围为 0.25 到 4：

```python
probabilities = softmax(logits / temperature)
```

温度以该类型在 calibration 上的平均软 CE 最小为准。
这是 NumPy 网格搜索，不涉及模型梯度；只得到三个标量：

| 类型 | calibration 题数 | 本次温度 |
|---|---:|---:|
| boolean | 180 | 1.0717734625 |
| choice | 180 | 1.0 |
| score | 240 | 1.0352649238 |

正温度保持候选分数的大小顺序，因此不会改变 argmax 一致率。
T>1 一般使分布更平缓，T<1 更集中。本次温度都接近 1，概率调整很小。
同类型的所有题共用一个温度，不是每个案例、每道题或每个 workflow 一个。

calibrate 中选择温度的源码摘录：

```python
for t in np.exp(np.linspace(np.log(0.25), np.log(4), 81)):
    ce = np.mean(
        [
            -(np.asarray(r["target"]))
            @ np.log(np.clip(probabilities(r["logits"], t), 1e-12, 1))
            for r in selected
        ]
    )
    candidates.append((float(ce), float(t)))
ce, t = min(candidates)
```

`selected` 是外层按题型筛出的校准题。每个 t 都对同一组已保存 logits 重算概率，
无需反复调用 Qwen3；min 按 `(ce,t)` 排序，优先选交叉熵最小的温度。

## 9. test 与本次结果

对应代码：[测试集读取、预测与输出](../scripts/train.py#L360)。

```python
test_rows = tokenize(load("test", prepared_dir), tok)
test_pred = evaluate(model, test_rows, pad)
cal_test = apply_calibration(test_pred, temps)
save(run_dir / "test_predictions.json", test_pred)
```

可以直接看到这里只有一次 evaluate；校准后的 cal_test 复用该次前向的 logits。

温度选择完成后才读取 test，模型只做一次前向生成 logits。
原始预测和用固定温度重算的概率分别存储，再输出两份报告。

| test 总体指标，2000题 | 未校准 | 校准后 |
|---|---:|---:|
| accuracy | 0.773000 | 0.773000 |
| soft CE | 0.857536 | 0.857080 |

## 10. 产物、耗时和复现边界

对应代码：[save](../scripts/train.py#L30)、[save_checkpoint](../scripts/train.py#L39)、
[selection 元数据](../scripts/train.py#L340)、[最终 report](../scripts/train.py#L366)。

| 文件 | 作用 |
|---|---|
| input_audit.json | train/dev 输入长度与题数审计 |
| initial_dev.json | 本次更新前的验证基线 |
| events.jsonl | 每次更新的损失、耗时及部分步的 dev 指标 |
| dev_step_N.json | 每次验证时的分组报告 |
| best.pt | 最佳模型 state_dict、step、protocol 和输入 schema 元数据 |
| selection.json | 决定选哪个 checkpoint，先于测试生成 |
| calibration_predictions.json | 校准集原始分数、概率和标签 |
| temperatures.json | 三种题型的拟合温度 |
| test_predictions.json | 测试集原始预测 |
| test_calibrated_predictions.json | 同一 logits 经温度处理后的预测 |
| report.json | 最终汇总及解释边界 |

`save()` 先写同目录临时 JSON，再替换目标文件；`save_checkpoint()` 对权重采用同样方式。
这减少中断时留下半个目标文件的风险，但没有做 fsync，不能理解为断电持久化保证。
best.pt 没保存优化器、scheduler、采样位置和随机数状态，所以不能靠它精确续训。

本次 selection 的 training_seconds 约 1202.98，计时从初始验证和初始保存之后开始，
包含训练期间 dev 与保存开销，不包含后续校准/test，也不是整个命令的启动到退出耗时。
peak_cuda_memory_gb=17.023 使用 max_memory_allocated / 1e9，
指 PyTorch 分配峰值的十进制 GB，不是 nvidia-smi 的整卡占用或 GiB。

本次 best.pt 内保存的 seed 是 20260921，当前 protocol 是 42。
分析已完成结果时以 checkpoint 快照为准；下一次运行会读取当时的 JSON，
不能承诺换成 42 后逐项得到相同数值。

如需自行运行，先按 [环境配置记录](../../docs/自己复现.md) 配置解释器。
以下命令均在 `text_jev_train/` 执行，使用新目录，并保留日志：

```bash

mkdir -p docs/执行日志
set -o pipefail

  --backbone models/Qwen3-0.6B-Base \
```
