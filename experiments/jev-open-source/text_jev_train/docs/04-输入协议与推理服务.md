# 04：jev_service 如何把请求变成决策结果

本文解释当前 jev_service 全部 Python 模块，并与 train.py 的训练路径对照。
没有在这里新增 HTTP 或共享前缀数值一致性实测；示例返回结构使用前文真实 CPU
前向概率说明，不能当成另一次服务性能测试。

## 1. 每个文件负责什么

| 文件 | 主要对象 | 职责 |
|---|---|---|
| [contract.py](../jev_service/contract.py) | semantic、prepare、encode_paths、answer | 统一输入、编码规则和输出格式 |
| [engine.py](../jev_service/engine.py) | DecisionEngine | 加载权重、组织推理、应用温度、返回用量 |
| [prefix.py](../jev_service/prefix.py) | common_prefix、encode | 候选编码的路径模式与共享前缀模式 |
| [server.py](../jev_service/server.py) | make_handler、main | HTTP 路由和错误响应 |
| [__init__.py](../jev_service/__init__.py) | 包说明 | 不执行加载或推理 |
| [scripts/serve.py](../scripts/serve.py) | main | 针对本目录训练产物的启动入口 |

调用链为：

```text
HTTP POST
→ Handler.do_POST
→ DecisionEngine.evaluate
→ prepare：规范化请求
→ encode_paths：完整候选token路径
→ prefix.encode：Qwen3候选向量
→ model._score：候选集合比较和评分
→ logits / 对应题型温度 → softmax
→ answer：转换成boolean、choice、score输出
→ HTTP JSON
```

训练只直接使用 contract 中的输入编码规则，没有通过 HTTP 或 DecisionEngine 训练。

## 2. contract.semantic()：语义输入的统一表示

对应代码：[contract.semantic](../jev_service/contract.py#L8)。对象和数组走下面的源码分支：

```python
if isinstance(value, (dict, list)):
    try:
        return json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(',', ':'), allow_nan=False)
    except (TypeError, ValueError) as exc:
        raise ValueError(f'{name} must contain valid JSON') from exc
```

字符串要求去掉空白后非空，但返回原字符串。
dict/list 转成 JSON 字符串，保持中文、按 key 排序、去掉多余分隔空格，并拒绝 NaN 等非法值。
这样 state 可以来自对象，也可以来自已经规范化的文本。

模型只编码 state、问题说明和候选描述。请求 id、题目 id、候选 key 用于对应和回传，
不会作为额外字段拼进 token。注意：state 自身若含某个业务 ID，那仍属于 state 内容，
不会被此函数自动剔除。

## 3. prepare()：三种题型变成统一候选列表

对应代码：[prepare 请求入口](../jev_service/contract.py#L19)、
[三类题的规范化分支](../jev_service/contract.py#L40)、
[总问题数与路径数限制](../jev_service/contract.py#L64)。

支持单请求：

```text
{"id": ..., "state": ..., "questions": [...]}
```

以及多请求封装：

```text
{"requests": [上述请求1, 上述请求2, ...]}
```

两者最终都得到 request 列表，每题有统一字段：

```text
id、type、text、keys、candidates
```

### boolean

固定 `keys=["true","false"]`。criteria 提供相应描述；缺省时使用 TRUE、FALSE。
真实 needs_review 的转换结果为：

```python
keys = ["true", "false"]
candidates = [
    "A human should inspect this run.",
    "No human attention is warranted.",
]
```

所以输出第一个概率永远对应 true，不按原请求字典里的 false/true 顺序决定。

### choice

options 是字典时，保留其输入顺序，key 作为返回值，value 作为编码的候选描述。
options 是列表时，key 自动编号为字符串 `"0"`、`"1"` 等。
真实 action 的 key 是 continue、human_review、observe、stop，
但模型看到的是各选项的英文描述。

### score

levels 是有序描述列表，key 按 `"0"` 到 `"N-1"` 编号。
模型仍然输出每个等级的概率，之后才计算期望分数，并非单个回归头直接预测数值。

主要限制如下：

| 项目 | 当前约束 |
|---|---|
| 一次请求封装的 state 数 | 1～32 |
| 每个 state 的 questions | 非空数组，题目 id 为不重复的非空字符串 |
| choice 候选数 | 2～255 |
| score 等级数 | 2～10 |
| 一次 evaluate 的问题总数 | 不超过 128 |
| 一次 evaluate 的候选路径总数 | 不超过 1024 |
| 同一道题的候选描述 | 不可完全重复 |

省略 type 时默认 choice；省略题目 id 时使用该题的位置字符串。

## 4. encode_paths()：训练与推理共享的文字编码

对应代码：[contract.encode_paths](../jev_service/contract.py#L68)、
[超长路径检查](../jev_service/contract.py#L79)。

每题每个候选各构造：

```text
[STATE] 状态文本
[QUESTION] 问题说明
[CANDIDATE] 当前候选描述
```

返回值是：

| 返回项 | 作用 |
|---|---|
| paths | 展开的完整 token 序列 |
| locations | 每条路径对应 `(全局题号, 题内候选号)` |
| question_rows | 展平后的题目元数据 |

全局题号会跨多个 request 递增，最后依靠原请求的问题顺序重新分组。
路径超过 max_tokens 时抛错，并明确说明未截断。
本项目不把 gold 或 target 接入这段编码。

## 5. DecisionEngine 初始化：服务加载的是什么

对应代码：[DecisionEngine.__init__](../jev_service/engine.py#L12)、
[scripts/serve.py 构造引擎](../scripts/serve.py#L41)。

初始化时完成：

1. 可选读取 temperatures.json。值必须有限且在 0.05～20 内，类型名限定三种。
2. 流式计算 checkpoint 的 SHA256，用于 info 返回模型身份。
3. 加载本地 tokenizer；无 pad token 时使用 eos。
4. 构建与训练相同的 AgentJevModel，再用 checkpoint 的 state_dict 严格加载。
5. 将模型置为 eval 并移到指定 device，准备一个线程锁。

服务需要本地底座目录和 best.pt 两者：底座目录提供 tokenizer、配置和初次模型加载，
best.pt 覆盖骨干及候选头权重。仅有底座不能得到训练后的候选头。
也不能只把 best.pt 交给通用 `AutoModelForCausalLM.generate()` 使用。

加载过程的关键摘录如下，中间的检查点类型校验见完整函数链接：

```python
self.model = AgentJevModel(model_path)
bundle = torch.load(checkpoint, map_location='cpu', weights_only=False)
```

校验后执行：

```python
self.model.load_state_dict(bundle['state_dict'], strict=True)
self.checkpoint_name = Path(checkpoint).parent.name
del bundle
self.model.eval().to(device)
```

第一步重建骨干和候选头的结构，第二步才将本次训练的完整 state_dict 覆盖进去。

这里没有校准集拟合、训练或教师 API 请求。若温度文件未提供，全部题型按 T=1；
文件中缺某种类型时，那一类也回退到 T=1。
`scripts/serve.py` 会自动尝试加载 run 目录中的 temperatures.json，缺失时允许未校准推理。

## 6. prefix.py：共享的是 Qwen3 前缀计算

对应代码：[prefix.common_prefix](../jev_service/prefix.py#L9)、
[prefix.encode](../jev_service/prefix.py#L17)、
[auto/shared/path 的选择](../jev_service/prefix.py#L28)。

服务先得到完整 paths，再决定如何计算候选向量。
因此共享前缀没有改变语义输入，只改变 Qwen3 的执行方式。

| encoder 模式 | 当前条件与行为 |
|---|---|
| path | 总是对完整路径编码，候选路径按 path_batch 分块 |
| shared | 每题有非空公共前缀时尝试共享；前缀为空则回到路径模式 |
| auto | 同题候选至少 8 个，且公共前缀至少 128 token 才共享 |

path_batch 默认 16，表示一次送入骨干的候选路径数，不是题数，也不是训练的梯度累积次数。
所有候选向量收集完毕后，才对完整候选集合统一调用 `_score()`；
不能把每块候选各自做一次集合评分并当作等价结果。

本地 prepared 的候选数是 2、4、5，所以当前数据在 auto 模式下都走 path 分支。
不是“设置 auto 后每一道题都会共享前缀”。`info.shared_prefix_compute=True`
只说明模式配置不是 path，实际命中数要看 `usage.shared_prefix_questions`。

auto 的条件直接来自源码，而不是按模型大小猜测：

```python
prefix_length=common_prefix([seq for seq,_ in entries])
use_shared=mode=='shared' or (mode=='auto' and len(entries)>=8 and prefix_length>=128)
if mode=='path' or not use_shared or prefix_length<1:
    fallback.extend(entries);continue
```

这里 entries 表示同一道题的所有候选路径。本例 action 只有 4 个候选，
即使前缀很长也不会满足 auto 的候选数条件。

共享模式逐题执行：

1. `common_prefix()` 找 token 级最长公共前缀，并给每条候选至少留下一个 token，
   以便提取其末 token 隐藏状态。
2. 将公共前缀单独送入骨干，用 use_cache=True 得到根 KV 缓存。
3. 把候选后缀分成小块；每块深拷贝根缓存，扩展 batch 维度后编码后缀。
4. 每条候选只看公共前缀和自己的后缀，不访问兄弟候选的 KV。
5. 取各候选最后有效 token，归位成 `[题数,Cmax,1024]`。

公共前缀可能包含 `[CANDIDATE]` 标记甚至候选描述的共同开头，
它按实际 token 比较，不是直接按 state/question 字段边界切开。
缓存只在这次编码中临时使用，不是跨 HTTP 请求的长期缓存。

对应的 [缓存复制与后缀编码](../jev_service/prefix.py#L45) 摘录：

```python
cache=copy.deepcopy(root_cache)
cache.batch_repeat_interleave(len(chunk))
hidden=backbone(input_ids=ids,attention_mask=attention,past_key_values=cache,use_cache=True).last_hidden_state
save(hidden,chunk,prefix_length);computed_tokens+=sum(map(len,suffixes))
```

deepcopy 保留根缓存供后续块复用，batch_repeat_interleave 给当前块的各候选分支提供对应缓存。

以真实 action 题为例，四条完整路径长为 `[105,107,109,104]`，合计 425 token；
`common_prefix()` 测得 98。强制 shared 时，理论上本实现记录的非 padding 骨干输入量是：

```text
98 + (105-98) + (107-98) + (109-98) + (104-98) = 131 token
```

425 和 131 是按路径长度推导的计数，不是本次新增的实际延迟或 FLOPs 测量；
代码仍有 padding、缓存拷贝、注意力和候选头等开销。
共享分支旨在保持独立因果路径的计算语义，但 BF16、不同批次和缓存实现可能带来数值差异，
本组文档没有重新验证两种模式逐项一致性。

## 7. 应用温度并返回三类答案

对应代码：[DecisionEngine.evaluate](../jev_service/engine.py#L48)、
[contract.answer](../jev_service/contract.py#L85)。

推理计算的源码核心为：

```python
vectors,mask,encoding_usage=encode(self,paths,locations,rows,self.encoder)
logits = self.model._score(vectors, mask).float().masked_fill(~mask, float('-inf'))
if self.temperatures:
    scaling=torch.tensor([self.temperatures.get(q['type'],1.) for q in rows],device=self.device)
    logits=logits/scaling[:,None]
probabilities = torch.softmax(logits, dim=-1).cpu().tolist()
```

scaling 是每题一个温度，`[:,None]` 扩成 `[题数,1]`，广播到该题的全部候选。
同一道题的分数一起除以 T，不是给不同候选分别拟合 T。

引擎把无效候选分数屏蔽为 -inf，按题型温度缩放 logits，再逐题 softmax。
随后 `answer()` 检查概率长度、非负与有限值以及总和，再生成业务字段。

### choice：返回 key、描述、最高概率和差值

用上文真实 CPU action 分布构造答案，其 choice 温度恰为 1：

```json
{
  "id": "action",
  "type": "choice",
  "distribution": {
    "continue": 0.089912,
    "human_review": 0.564414,
    "observe": 0.280673,
    "stop": 0.065001
  },
  "value": "human_review",
  "description": "Queue this trace for a human to review.",
  "top_probability": 0.564414,
  "margin": 0.283741
}
```

数值经四舍五入，margin 是第一与第二大概率之差，不是正确率。
这份结构示例并非新启动 HTTP 服务取得的响应。

### boolean：probability 永远表示 true 的概率

对应代码：[answer 的 boolean 分支](../jev_service/contract.py#L91)，源码为：

```python
if question['type'] == 'boolean': out.update(probability=probabilities[0], value=probabilities[0] >= .5)
```

`probability=probabilities[0]`，`value = probability >= 0.5`。
如果将真实教师分布 `[0.666667,0.333333]` 直接交给 answer，会得到 value=true；
实际服务交给 answer 的是模型经温度调整后的分布，不是这个教师标签。

### score：返回期望与最大概率等级

对应代码：[answer 的 argmax](../jev_service/contract.py#L89)、
[score 格式化分支](../jev_service/contract.py#L96)。

`score = sum(i * p_i)`，`level = argmax(p)`，legend 保留等级描述。
用真实 risk 教师分布演示格式：期望为 1.673333，最大概率等级为 2。
两者含义不同；score 也不会被自动归一化为 0～1。

顶层响应按原 request 分组，包含 `results=[{id,answers:[...]}]` 和 usage。
generated_tokens 固定为 0，因为没有文本解码循环。
`input_path_tokens` 和 `backbone_input_tokens` 均按非 padding 长度累计，不能当作实际算子工作量。
`wall_ms` 从 token 化之后开始，包含锁等待及后续推理/组装开销，
不等于整个 HTTP 往返时间。

## 8. HTTP 层、启动方式与当前边界

对应代码：[server.make_handler](../jev_service/server.py#L8)、
[POST 解析与错误处理](../jev_service/server.py#L23)、
[scripts/serve.main](../scripts/serve.py#L19)。

`ThreadingHTTPServer` 接收请求，引擎内部锁将模型计算串行化，
不能因为 HTTP 是线程服务器就认定 GPU 同时跑多个请求。

| 路由/情况 | 行为 |
|---|---|
| GET /health、/api/info | 返回 ready、模型、checkpoint SHA256、温度等信息 |
| POST /api/evaluate | 解析 JSON，执行决策推理 |
| POST 长度不在 1～1000000 字节 | 413 |
| 非法协议字段或 JSON 值等 | 通常 400 |
| 推理过程中其他异常 | 500，详细异常写终端 |
| 未知路由 | 404 |
| GET / | 尝试读取静态 HTML 页面 |

当前目录没有 `jev_service/web/index.html`，所以默认首页不能据此保证可用。
`/health` 和 `/api/evaluate` 的处理不依赖该页面文件。
server.main 还保留另一套启动默认值，本目录优先使用 scripts/serve.py 显式传入路径。

POST 最终交给引擎的这一行是整个 HTTP 层到模型计算层的连接点：

```python
self.send_json(200, engine.evaluate(payload))
```

它位于 do_POST 的 try 中；协议异常和模型异常分别由后面的 except 分支映射为响应。

在 `text_jev_train/`、已激活环境时启动：

```bash
mkdir -p docs/执行日志
set -o pipefail
python scripts/serve.py \
  --run-dir runs/agentjev_v1 \
  --backbone models/Qwen3-0.6B-Base \
  --device cuda:0 --encoder path --port 8149 \
  2>&1 | tee docs/执行日志/文本推理服务.log
```

这里显式用 path 方便先按独立路径核对。serve.py 不导入 train.py，
因此训练脚本中覆盖 CUDA_VISIBLE_DEVICES 的代码不在这条服务启动链执行。
服务默认只绑定 127.0.0.1，`--host` 可显式改变监听地址。

在另一终端检查服务，并直接发送 prepared 中的真实第一条请求：

```bash
curl -s http://127.0.0.1:8149/health
python -c 'from pathlib import Path; print(Path("prepared/train_requests.jsonl").open().readline(), end="")' \
  | curl -s http://127.0.0.1:8149/api/evaluate \
      -H 'Content-Type: application/json' --data-binary @-
```

该请求包含五题、18 条候选路径；响应应包含该案例的五个 answers。
这是接口连通性和结构检查，输入来自训练集，不能拿它替代独立 test 评估。
